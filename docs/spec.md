# FDE Project 4: Ask-your-data agent (text-to-SQL)

Spec v1, 2026-11-10. Part of the FDE Portfolio (vault: `Projects/In progress/FDE Portfolio`). Same fictional customer: Larkfield Coffee Co. (disclose as simulated).

## The customer problem
Larkfield's ops and marketing leads ask the one analyst questions all day ("returns rate for grinders last quarter?", "top 5 beans by revenue in Bengaluru?"). Goal: a chat agent that answers from the BI warehouse by writing SQL, shows the SQL and the result, never writes or leaks personal data, and is measured on a gold question set.

## Stack (local only, no installs beyond the existing venv)
Python 3.13, FastAPI, httpx, psycopg 3, Postgres (Docker, image `pgvector/pgvector:pg17` already pulled, port 5435), pytest, ruff. Venv: `.venv` (reuse; install nothing). LLM: Ollama `http://localhost:11434/api/chat`, model `fusion27b:iq3`, `"think": false`, `"stream": false`; provider switch for Anthropic like project 1 (`../fde-support-agent\app\llm.py` is the reference implementation; copy, do not import). Chat templates reject a system message that is not first: only one system message per request. (audit 2026-11-10) The model name lives in settings (env `OLLAMA_MODEL`) and is read on every call, not cached at import, so project 5 can switch models in-process. API on port 8400 (8000/8100/8200/8300/9000 are taken).

## Warehouse (`warehouse/`)
- Deterministic generator (seeded) for 12 months (2025-11-01 to 2026-10-31) of a star schema: `dim_date`, `dim_product` (reuse the 50 products in `../fde-support-agent\data\products.json`), `dim_customer` (about 2,000; city, state, signup channel; name/email/phone present for realism), `fact_orders` (about 8,000; channel, city, payment method, shipping method, discount), `fact_order_items`, `fact_returns` (reason, refund amount), `fact_tickets` (category, first response hours, resolved flag). Realistic seasonality (Diwali spike) and a few known patterns to ask about.
- `schema_docs.yaml`: one line per table and column (meaning, units, allowed values). This is what the agent reads.
- Two roles: an owner role for loading and `analyst_ro` with SELECT only on the facts and dims, and NO access to customer name/email/phone columns (use a view `dim_customer_safe` without PII and grant only that).

## Agent (`app/`)
1. Question in; build prompt from `schema_docs.yaml` plus a few sample values per low-cardinality column.
2. LLM returns SQL in a fenced block plus a one-line plan.
3. Guardrails before execution: single statement; must start with SELECT or WITH; reject any DDL/DML keywords outside string literals; tables must be in the allowlist; add `LIMIT 200` if absent; run as `analyst_ro` inside `BEGIN READ ONLY` with `statement_timeout = 5s`. (audit 2026-11-10) The database is the control that must hold; the parser is defence in depth. Set the timeout on the role (`ALTER ROLE analyst_ro SET statement_timeout`) as well as per session, and give `analyst_ro` no privilege on raw `dim_customer`.
4. On a database error, one self-correction round with the error message.
5. Answer: the SQL, the result rows (max 50 shown), and a one-to-two sentence summary written from the actual rows (numbers must come from the rows). (audit 2026-11-10) Checked in code: every number in the summary must appear in the rows (after rounding to the precision shown); if not, drop the summary and show rows only, and log it.
- (audit 2026-11-10) Contract for project 5 (its adapter imports these, so keep the names): `app.agent.ask(question: str) -> dict` with keys `sql`, `columns`, `rows`, `summary`, `refused` (bool), `refused_reason`, `usage` (`prompt_tokens`, `completion_tokens`, `latency_ms`); never raises. `evals/scoring.py` has a pure `score_case(case, result) -> {"passed", "checks", "reasons"}` that takes a database connection only through an argument.
6. Refuse: write requests, PII requests (emails, phones, names of customers), questions the schema cannot answer (say what is missing).
- `POST /ask` API and a minimal local HTML page (no external CDN).
- Every request logged (question, SQL, rows returned, latency, tokens, refused reason) to `logs/requests.jsonl`.

## Eval (`evals/`)
- `gold.jsonl`: 40 questions with gold SQL, written and checked against the generated data: 25 single-table/aggregate, 10 joins/time windows/ratios, 5 must-refuse (DML, PII, unanswerable). Write them before running the agent; never change a gold item after seeing the agent's output in that run; a rule change goes in its `notes` before the next run. (audit 2026-11-10) Field `category` is exactly `simple`, `complex` or `refuse` (project 5's gate uses `refuse` as must-pass across suites). Few-shot examples in the prompt must not be gold questions or paraphrases of them, and nothing under `app/` reads `evals/`. "Top N" gold questions use an ORDER BY with a tie-breaker so ties cannot flip the result.
- Metric: execution accuracy. Run gold SQL and agent SQL, compare result sets (order-insensitive unless the question asks for an order; numeric tolerance 0.01; column names ignored). Refuse cases pass if no SQL is executed and the reply declines. (audit 2026-11-10) Extra columns are allowed: pass when the row counts match and every gold column matches some agent column by value (an agent that adds a product name next to the id still passes). Gold SQL goes through the same `LIMIT 200` rule as agent SQL. Also report summary faithfulness (share of answers whose summary passed the number check). (review 2026-11-10) Scoring tightened before the first live run: each gold item has an explicit `precision` (the agent value is rounded to it and must match exactly; a coarser value fails; `null` = unrounded gold with 0.5% relative tolerance); extra agent columns are allowed only if non-numeric (the number of numeric columns must equal gold's, so hedging with two candidates fails); boolean label columns accept text labels from a per-item `label_map` and swapped labels fail; a summary-LLM failure never fails a case with correct SQL (recorded as `summary_error`); refuse cases also check `refused_reason` against `refuse_kind`. (orchestrator 2026-11-10, after live run 1, before live run 2) The extra-column rule is refined: an extra numeric agent column is allowed only when (a) the gold row has no numeric column (the answer is a label) or (b) every gold numeric column is non-integer valued (a rate, share, average, growth) and every extra agent numeric column is integer valued (a count); gold numeric columns must still be matched at the declared precision; two competing counts, two competing averages, or an extra number beside an integer gold answer still fail. Live run 1 is not rescored.
- Baseline: same model with only table names (no `schema_docs.yaml`, no sample values). (review 2026-11-10) Two baselines: `ddl` = the raw CREATE TABLE text of the allowed tables plus "Today is 2026-11-10", nothing else (the standard comparison); `floor` = the table-names-only run above. `python -m evals.run --variant all` runs agent, ddl, floor.
- Report `evals/report.md`: accuracy by category for agent vs baseline, guardrail blocks, p50/p95 latency, tokens per question, failed questions with the SQL produced. (review 2026-11-10) Wilson 95% intervals on every accuracy figure, refusals split by source (pre-filter, model, parser, database), summary-call errors, and a note on what G26 and G28 cannot distinguish.
- Unit tests with a mocked LLM: guardrails (every bypass attempt you can think of: comments, semicolons, CTE with DELETE, `pg_sleep`, `COPY`, `SET ROLE`; audit 2026-11-10: also `set_config`, `pg_read_file`, `lo_import`, `dblink`, `SELECT ... INTO`, `FOR UPDATE`), result comparison, prompt building. (audit 2026-11-10) Plus one integration test against the real DB that skips the parser and runs, as `analyst_ro`, an INSERT, a DELETE, a CREATE TABLE and a `SELECT email FROM dim_customer`, and asserts each one fails with a permission or read-only error. Live LLM runs only when the owner/orchestrator runs the eval (GPU is shared; do not call Ollama during the build).
